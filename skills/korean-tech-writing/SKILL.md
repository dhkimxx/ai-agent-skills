# 한국어 기술문서 작성

기술 문서의 목적은 **독자가 이해하고 재현하는 것**이다. 이 스킬은 "낯선 용어 때문에 감이 안 온다"는
피드백을 줄이려고 만든 작성 규칙이다. 특정 제품·프로젝트 지식이 아니라
**모든 CS·프로그래밍 분야에 적용되는 문서 작성 관례**다.

- 발행 전 점검: `checklist.md`
- 규칙의 출처: `references.md`

## 1. 3원칙

1. **독자를 먼저 정의하라.** 문서 첫머리에 "독자 수준 + 선행 지식 + 읽는 시간"을 한 줄로 밝힌다.
   (예: "웹 개발 경험 있음 · 도커는 처음 · 약 20분") — 전문가의 **지식의 저주**를 경계한다.
2. **쉬운 말 먼저, 정확한 용어는 병기하라.** 처음부터 어려운 용어로 시작하지 않는다.
   첫 등장에서는 `멱등성(idempotency)`처럼 **한글(영어)** 로 쓰고, 이후에는 하나로 통일한다.
3. **한 문장 = 한 개념.** 40자 안팎을 목표로 한다. 길어지면 표·목록·문단으로 쪼갠다.

## 2. 문서 유형 6종 — 먼저 유형을 고른다

| 유형 | 독자·목적 | 문체 | 용어 밀도 | 골격(1줄) |
|---|---|---|---|---|
| **튜토리얼**(따라하기) | 처음 시작 · 성공 경험 | "~하세요" | 최대 | 준비물(버전) → 단계(동사 시작·예상 결과) → 확인 → 다음 |
| **하우투**(문제해결) | 이미 씀 · 문제 해결 | "~한다" | 중간 | 증상(에러 원문) → 원인 후보 → 해결 → 검증 → 예방 |
| **레퍼런스**(사전) | 익숙 · 찾아보기 | 건조·정확 | 최소 | 개요 1단락 → 항목 표(기본값·타입) → 예제 → 주의 |
| **설명**(개념) | 궁금 · 이해 | 교재체 | 높음 | 정의 → 왜(문제) → 원리 → 예시·반례 → 관련 개념 |
| **교재**(장) | 학습 · 체계적 습득 | 교재체 | 최대+점진 | 표지(요약·목표·그림·지도) → 절 → 요약·문제 → 부록 |
| **브리프**(1~4p) | 판단 · 요약·의사결정 | 핵심 위주 | 필요한 만큼 | 요약(결론) → 왜(숫자) → 실체 → 읽는 법 → 더 볼 것 |

골격은 **출발점일 뿐**이다. 문서마다 상황에 맞게 줄이거나 늘린다.
한 문서에 여러 유형을 섞어야 하면 **주 유형을 정하고 나머지는 부록으로** 분리한다
(레퍼런스 표를 설명 글 본문에 끼워 넣지 않는다).

## 3. 용어를 "중간중간 교과서처럼" 푸는 패턴 (핵심)

별도 용어집만 두면 아무도 찾지 않는다. **본문에서 만나는 순간** 풀어준다. 8가지 중 골라 쓴다.

### A. 인라인 정의 (가장 흔함)
첫 등장에서 **한 줄 정의 + 괄호 비유**. 이후에는 용어만 쓴다.
> **멱등성(idempotency)** — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. *같은 버튼을 여러 번 눌러도 엘리베이터가 한 번만 움직이는 것.*

### B. 설명 상자(콜아웃) — 문서당 2~5개
용어가 **문서 이해를 좌우할 때**만. 4칸: (1) 뜻 (2) 비유 (3) 없으면/모르면 생기는 일 (4) 이 시스템 예.
> **트랜잭션 격리 수준(isolation level)** — 동시에 도는 트랜잭션끼리 서로 얼마나 보이게 할지 정하는 규칙.
> *회의실 커튼을 어디까지 칠지.*
> 모르면: 재고 차감이 두 번 일어나는 유령 읽기(phantom read) 같은 버그를 못 찾는다.
> 이 서비스: 주문/결제는 `REPEATABLE READ`, 통계 조회는 `READ COMMITTED`.

### C. 명사구 뒤 괄호 비유 (흐름을 끊지 않을 때)
> CDN(콘텐츠 전송망)은 사용자 동네마다 두는 물류 창고다.

### D. 표의 "뜻" 열
용어가 여럿 나열될 때: `용어 | 쉬운 뜻 | 이 시스템 예`.

### E. "이 장의 용어" 미니 표 (장 시작)
그 장에서 처음 나오는 낯선 용어 5~8개를 미리 소개한다. 심화는 본문에서.

### F. 이름 해독 표 (디코더)
규칙성 있는 이름은 **읽는 법**을 가르친다. (암기 대상 아님)
> HTTP 상태코드: `2xx` 성공 · `3xx` 다른 주소로 이동 · `4xx` 요청 오류 · `5xx` 서버 오류
> 암호화 이름: `AES-128-GCM` = 알고리즘(128비트 키) + 모드(GCM, 무결성 포함)

### G. 점진적 공개 (3단계)
(1) 한 줄 정의(본문) → (2) 동작·예시(같은 절 뒤) → (3) 정밀 정의·예외(부록).
한 번에 다 설명하지 않는다.

### H. "문제 → 해결" 역순 설명
기법을 먼저 말하지 말고 **문제를 먼저** 보여준다.
> (X) "N+1 쿼리 방지를 위해 eager loading을 쓴다."
> (O) "목록 한 건마다 쿼리가 한 번씩 나간다. 100건이면 101번 질의한다. 그래서 한 번에 묶어 가져온다 — 이것이 eager loading이다."

## 4. 문체 규칙

| 항목 | 규칙 |
|---|---|
| 종결 | 문서 유형에 맞춰 통일 (교재·설명: "~한다/~이다", 튜토리얼: "~하세요") — **한 문서에서 섞지 않는다** |
| 태 | **능동태 우선**. "~에 의해 처리된다" → "스케줄러가 처리한다" |
| 시제 | **현재 시제**. "값을 반환했다" → "값을 반환한다" (과거 사건 서술은 예외) |
| 인칭 | 독자를 **2인칭으로 직접 부른다** — "사용자는 설정해야 한다"보다 "설정하세요" |
| 순서 | **조건을 먼저, 지시를 나중에** — "X일 때 A를 한다"(O) / "A를 한다. X라면"(X) |
| 동사 | 구체 동사 — "처리한다"보다 "검증한다/변환한다/저장한다" |
| 대명사 | 모호하면 **명사를 반복**(이것/그것/그 남용 금지). 지시 대상과 5단어 이상 떨어지면 반복 |
| 문장 연결 | 같은 조사·접속사를 연달아 쓰지 않는다. 이중 부정 금지 |
| 번역투 금지 | "~되어진다", "~에 의해", "이것은 ~이다", "~에 대해서", "~를 통해" 남용, 영어 어순 직역 |
| 금지 표현 | "쉽게/간단히/그냥/무조건" — 독자를 탓하거나 과장하는 표현 |
| 주어 | 행위자가 헷갈리면 **명시** (누가 하는지가 기술 문서의 핵심) |
| 강조 | 굵게는 문단당 1~2회. 남용하면 강조가 사라진다 |
| 나열 | 3개 이상은 문장이 아니라 목록/표로 |

## 5. 표기 규칙

- **용어**: 첫 등장 `한글(English)` → 이후 하나로 통일. 코드·식별자·고유명은 원문 유지(`docker compose`, `window.location`).
- **약어**: 첫 등장에 풀어쓰기 — `CDN(Content Delivery Network)`. 여러 번 쓰지 않으면 풀어쓰지 않는다.
- **제품·상표**: 번역하지 않고 **원문 대소문자를 유지**한다(`GitHub`, `npm`, `JavaScript`).
- **개발 용어**: 개발자가 쓰는 관용 표기를 따른다 — 버그(O)/벌레(X), Ctrl(O)/컨트롤(X).
- **한글 표기**: 표기가 갈리는 용어는 TTA 정보통신용어사전을 1차 기준으로 삼는다.
- **조사**: `은(는)` 같은 병기 대신 하나로 확정한다(어려우면 범주를 명시).
- **수치**: 단위와 함께 쓴다(`128 MB`, `p99 320 ms`). "약/최대/중앙값"을 밝힌다.
- **근거 표기**: 측정값과 주장에는 출처 태그를 붙인다. 기본 세트 —
  `[검증]`(실행·재현으로 확인) · `[측정]`(수치 실측) · `[추정]`(정황 근거) · `[인용]`(문서·코드 인용).
  프로젝트 관례가 있으면 그 관례를 따른다(프로젝트 문서에서 정의한다).
- **버전·시점**: 문서 상단에 "기준 버전·날짜"를 밝힌다(`기준: v2.4.0, 2026-09`). 버전이 바뀌면 갱신 책임자를 명시한다.
- **문장부호**: 가운뎃점(·)은 동급 나열, 화살표(→)는 흐름. 마침표로 끝나면 완전한 문장, 아니면 명사구.
- **코드/경로**: 모노스페이스(백틱)로 쓴다. 길면 코드 블록으로 빼고 실행 결과를 함께 보여준다.
- **비유**: 한 용어에 비유 1개. 비유 직후 **실제 정의를 반드시** 붙인다.

## 6. 구조·그림·표 규칙

- 그림·표는 **번호와 제목**을 붙이고 본문에서 반드시 참조한다("그림 2 — ...").
- 표 머리글은 굵게, 단위 열을 명시한다. 긴 표는 "핵심 열만" 남기고 부록으로 뺀다.
- 도식은 **박스 + 화살표**로. 박스 문구는 15자 이내로 줄인다(넘치면 줄바꿈).
- 코드 예제는 **복사해서 바로 돌아가는 최소 단위**로. 실행 결과·예상 출력을 함께 보여준다.
- 각 절은 **"왜 이걸 알아야 하나"** 1문장으로 시작한다.
- 목록은 **병렬 구조**로 쓴다. 순서가 중요하면 번호, 아니면 불릿. 번호 단계는 **동사로 시작**한다.
- 목록·표는 **도입 문장**으로 소개하고 콜론으로 끝맺는다("다음 표는 …").
- 문서 첫머리에 **다루지 않는 것(out of scope)**을 한 줄로 밝힌다(기대 관리).
- 참고 링크는 문장 중간에 흩뿌리지 말고 **하단에 모은다**.

## 7. 출력 시 주의 — 한국어 글리프

한국어 문서를 PDF·이미지로 만들 때 **글자가 조용히 사라지는** 일이 잦다.

| 함정 | 원인 | 대처 |
|---|---|---|
| 본문·그림에서 사라짐 | 한글 폰트에 없는 기호(`Σ`, `−`, `①`, `✅` 등) | ASCII로 대체(`sum`, `-`, `1.`) 또는 폰트 추가 |
| 코드블록에서 사라짐 | 한글을 코드용 모노폰트로 그림 | 폰트 런 분리(ASCII·기호는 모노, 한글은 한글 폰트) |
| 표에서 사라짐 | 셀 폰트가 기호를 미지원 | 발행 전 글리프 검사기로 전수 확인 |

- 발행 전 **글리프 검사**(폰트 커버리지와 사용 문자를 대조)를 반드시 1회 돌린다.
- 검사기·폰트·경로 같은 구체 사항은 프로젝트 문서(README·기여 가이드)에 적는다.

## 8. 작성 프로세스와 체크리스트

**작성 6단계**: (1) 요구사항 — 왜·누가 읽는가 → (2) 개요 — 유형 선택 + 목차 →
(3) 초안 — 구조 먼저 → (4) 자가 점검 — `checklist.md` → (5) 리뷰 — 동료 1인
(초보자 대상이면 **초보자 리뷰어**) → (6) 발행 — 버전·날짜 명시.

핵심 5항 (전체는 `checklist.md`):

1. 낯선 용어가 **첫 등장에서** 풀렸는가?
2. 같은 개념에 같은 단어를 썼는가? (타일/조각/블록 혼용 금지)
3. 모든 수치에 단위와 근거 태그가 있는가?
4. 그림/표를 본문에서 참조했고 번호가 맞는가?
5. 소리 내어 읽었을 때 어색한 문장이 없는가?

선택 도구: 한국어 산문 린터(예: `hanlint`)로 번역투·이중 피동·명사 나열을 자동 점검한다.

## 9. 안티패턴

- 용어를 영문 그대로 툭 던지기: "레이턴시를 줄인다" (정의 없이)
- 비유만 하고 실제 정의 생략: "택배 상자 쌓기처럼 하면 된다"
- 한 문장에 개념 3개: "커넥션 풀을 늘리며 타임아웃을 조정해 p99를 낮춘다"
- 같은 것을 다른 말로: 응답/리턴/결과 혼용
- 강조·이모지 남용, 과장("엄청 빠른", "혁신적")
- 독자 탓 표현: "간단히 ~하면 된다", "그냥 ~를 쓰면 된다"
- 조건을 뒤에 붙이기: "A를 누른다. (설정이 꺼져 있다면)"
- 검증 안 된 수치 단정, 출처 없는 일반화
- 유형 혼합: 설명 글에 레퍼런스 표를 통째로 붙이기

## 10. 프로젝트 관례가 있으면 그것을 우선한다

이 스킬은 **도메인 중립 기본값**이다. 프로젝트에 정한 관례가 있으면 아래 항목은 그 관례를 따른다.

- **근거 태그**: `[검증]`/`[측정]`/`[추정]`/`[인용]` 대신 사내 태그를 쓸 수 있다.
- **문체**: 합쇼체/평서체 선호, 금지 표현 목록.
- **출력·도구**: 폰트, PDF/HTML 변환 도구, 글리프 검사 명령.
- **용어집**: 프로젝트 용어집 파일 경로 — 첫 등장에서 정의한 용어를 여기에도 추가한다.

규칙 본문을 프로젝트마다 복사하지 않는다. 이 스킬을 참조하고, 위 항목만 프로젝트 문서(README·기여 가이드)에 적는다.
